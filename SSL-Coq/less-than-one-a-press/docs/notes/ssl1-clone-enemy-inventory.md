# SSL Area 1: cloned enemies, their sizes, and a fresh collision gap

This is a source inventory and a conditional sizing comparison, not a new no-A route. The stock sources are pinned to `9921382a68bb0c865e5e45eb594d9c64db59b1af`; the existing proofs use the actual generated US/JP Clight. The user now grants a chosen cloned enemy's X/Y/Z placement, potentially using a HOLP carried from another level. That lets us test the transfer without constructing the clone/HOLP route. It does **not** grant a chosen hitbox size, arbitrary memory changes, or a stock enemy that the game never creates.

Here, **position** means X/Y/Z. **Dimensions** mean the live hitbox height, radius and downward offset, together with the graphics scale that may update them. A bigger-looking animation is not automatically a bigger collision box. A supplied alternative height below is a sensitivity calculation unless a stock size-changing operation is identified.

## What “cloneable” means in this inventory

There are three different claims. Bob-ombs and the small/jumping boxes can be picked up through the ordinary grabbable handler. A different enemy can be acquired through a **fake pickup** if the pickup's remembered object slot unloads and that particular initialized enemy occupies it before the pickup animation completes. Finally, a controller-only replay would have to construct the required fake pickup under the allowed A-button history. This batch does not supply that last replay for any named enemy.

The source explicitly documents fake pickups in `act_picking_up`. `mario_grab_used_object` takes the remembered slot, without a species whitelist. For an object lacking `OBJ_FLAG_HOLDABLE`, `obj_set_held_state` switches its current behavior command to a carry script. Those scripts execute `BREAK`, which stops script processing without deactivating the object. They do not rerun the enemy constructor or enlarge its hitbox. Existing dimensions, interaction type and subtype can therefore matter. An already intangible or inactive object does not become a usable bounce target merely because its slot was grabbed. An allocated but not yet initialized actor begins with height 100, radius 50 and intangible timer -1; it cannot simply be treated as the fully initialized species in the table.

Dropping supplies Mario's current movement Y and the HOLP's X/Z. Throwing supplies the HOLP's Y and X/Z plus a 32-unit horizontal offset. Neither changes scale or hitbox dimensions. The new placement grant defers the controller history supplying those values; species capture, initialization, tangible contact and the later copies still need their own checks. Transport cloning's object-object collision correction changes X/Z, rather than height.

## What placement can and cannot buy

For a newly created upward movement/collision gap, let Mario start with movement Y = raw collision Y = display Y = 768. Let the enemy's live origin be E and live height H. The actual hit-from-above test requires Mario's movement Y **strictly above E**, with an airborne action, negative vertical speed and no earlier attack classification. A normal bounce then writes movement Y = binary32(E + H). Therefore lifting an enemy arbitrarily high cannot leave Mario at 768 and still pass this guard. To maximize the fresh snap at this starting height, put E just below 768, rather than thousands of units above it.

The supplied sizing recipe is enemy `(-2200,767.99993896484375,-1024)`, the closest binary32 origin below 768, with initialized/tangible dimensions, positive overlap radius, and the actual reached helper/read conditions. This is a conditional local calculation, **not** a valid full installation-frame replay. Mario at the original `(-2200,768,-1024)` is already in warp contact: in the normal falling-contact case, the earlier warp handler stops the ordinary interaction pass before the later enemy bounce. An illustrative outside-contact comparison instead places Mario and enemy at X=-2400, Z=-1024, retaining these same Y values. That removes this particular warp-contact obstacle, but Mario's actual floor/action pose is still a supplied condition; it is not a newly reached gameplay state.

These arithmetic diagnostics used binary32 casts for each addition; they are not detected emulator gaps or a newly verified Float32 certificate. In particular, rounding matters near the exact top. The displayed top is 1938.8648681640625: using H equal to its arithmetic gap in this recipe lands one binary32 value below it. Raising supplied H to the next float puts this recipe one value above it. Neither supplies a real resizing mechanism.

The Coq result is more conservative and more general than this table: [InkBounceApproachGap.v](../../proofs/InkBounceApproachGap.v) proves a new **upward** rise of at most 251 when the actual compared movement/actor reads match the bounce-entry reads, the explicit finite numeric ranges hold, and live H≤250. From synchronized incoming records, `ibag_completed_bounce_creates_at_most_251_synchronized_gap` carries that bound to both M−C and M−D at the actual height store, independent of chosen actor placement. This is a signed upward bound, not an absolute-gap bound. The separate fresh-contact obstruction in `InkBounceProducerEffect.v` addresses downward snapping under its stated overlap/down-offset conditions.

If collision Y was already low before the bounce, the total M−C gap equals the inherited disagreement plus this new rise. The fresh bound does not erase that inherited producer question. A small enemy can also convert an inherited high-movement/low-collision disagreement into a raised-display/low-movement disagreement at the snap: supplied M=D=1938.8648681640625, C=768 and enemy E=693, H=75 would snap movement to 768 if the actual contact/helper checks are reached. That calculation inherits the large disagreement; it does not create it from synchronized records. Subsequent upward flight adds travel, not automatically a surviving disagreement between records. The completed-callback copy result below now closes the collision gap at that boundary in its stated scope.

## The negative-size Fire Fly Guy

The supplied shrinking demonstration describes the same source operation: repeatedly interrupting facing resets the timer while scale velocity keeps decreasing. Passing through zero can make the rendered object look large again with **negative** scale. `obj_set_hitbox` multiplies the signed Y scale into height and the signed X scale into radius; it does not take their absolute values. Chosen position does not turn those negative dimensions into a normal giant enemy.

The actual collision routine first requires the sum of Mario's and the enemy's radii to be greater than horizontal distance. Mario's normal script radius is 37. A sufficiently negative enemy radius therefore misses even at zero horizontal distance. In the special matched-uniform-scale calculation, Fly Guy radius is 70s and height is 60s: contact needs s greater than roughly -37/70, so this calculation cannot supply a large negative height. This ratio is **not** a proved all-history invariant. Fly Guy copies the preceding X scale to Y at frame start, then its action may change X before the hitbox update. A mixed-sign radius/height phase has to be checked using those separate live reads. The named upward steps are small (+0.06 at the start of fire growth or +0.02 toward the idle size); they do not identify a stock transition from a very negative Y scale to a large positive X scale.

Vertical collision supplies an independent restriction. Writing C for Mario's raw collision bottom and E for an enemy with zero down offset, the tested endpoints are binary32(E+H) and binary32(C+MarioHeight). Contact requires C no higher than the enemy's tested top, and Mario's tested top no lower than E. With finite ordinary values, a very tall inverted negative hitbox cannot fit inside Mario's 100- or 160-unit vertical span, regardless of chosen enemy position. The approximate span argument here is source arithmetic, not a new rounding-certified universal -160 threshold.

The existing Coq result is sharper for the bounce we care about: `ibp_fresh_contact_bounce_cannot_snap_below_collision` proves that a reached bounce with matched actual zero-down-offset contact reads cannot put movement below raw collision Y. It does not need the upward theorem's H≥-32768 assumption. Starting with M=C, a negative-height/zero-down-offset enemy also cannot satisfy both fresh vertical contact and the normal hit-from-above guard M>E. Inherited record disagreements and changed fields between detection and consumption remain distinct questions. The video's eventual invalid float-to-integer conversion or crash is outside the defined execution model; this investigation stops before that.

## What remains

The position grant removes placement construction from this local sizing batch. We still need a legitimate initialized enemy in the reused pickup slot, the live dimension/tangibility history, and the actual interaction ordering. The source review identifies stock size changes; it does not discharge an all-history live-height bound. With synchronized incoming records and H≤250, the direct bounce snap cannot create the 1093-unit Variant collision gap. Large negative Fire Fly Guy scale, inherited position disagreements, repeated flight/copy histories and other hazard handlers must retain their distinct checks. No controller-only clone witness or complete Ink route is established here.

## The fresh collision split does not survive the completed callback

The follow-up [bounce collision-lifetime result](ink-bounce-collision-lifetime.md) connects the mandatory movement-to-collision copy to the same Mario update. At that copy, collision Y becomes the actual movement Y, erasing the bounce's fresh M−C disagreement. The full-return theorem covers the completed Mario callback with its stated ordinary storage conditions and zero-particle return path; it is not a blanket result for every later callback or every gameplay history.

The finite runtime batch used 16 supplied poses, of which 12 produced a bounce. All 384 recorded end checkpoints had movement, collision and display Y equal. These are finite transfer checks, not a no-A clone route or an exhaustive search. The chosen enemy-position grant still supplies position only, and neither these tests nor the nominal table establish a universal all-history maximum gap. The useful new conclusion is that the fresh collision split must be consumed before the mandatory copy if this particular producer is to help.
